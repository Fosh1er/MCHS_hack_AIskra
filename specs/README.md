# Спецификации пунктов плана — трассировка «задача → реализация»

Один файл на пункт [плана работ](../docs/brief/02_План_работ.md), имя файла — `<пункт>-<кратко>.md`. Пункт плана → требования → код → тесты → статус видны в одном месте: проверяющему и следующему агенту не нужно искать по репозиторию.

## Структура файла
Шаблон — [_template.md](_template.md).

1. **Пункт плана** — текст пункта из плана капитана, без пересказа: фронт работ, документация, материалы.
2. **Требования** — фронт работ, разбитый на атомарные требования с идентификаторами `R<пункт>-NN`, например `R0.2-04`.
3. **Трассировка** — таблица: требование → где реализовано (файлы, эндпоинты, таблицы) → чем проверено (тесты или ручная проверка) → статус.
4. **Решения** — ссылки на ADR и почему сделано так.
5. **Критерии приёмки** — чек-лист.
6. **Отклонения, долги, открытые вопросы** — что сделано не как в плане и почему, что перенесено в другие пункты.
7. **Детали** (по необходимости) — исследование источников, модель данных, API.

## Правила
- **Сначала спецификация, потом код.** Перед началом пункта создайте файл по шаблону: разделы 1–2, статус «не начато».
- **Трассировка обновляется в том же коммите, что и код.** Статусы:
  - ✅ сделано и проверено;
  - 🟡 частично (в столбце «Примечание» — что именно не сделано);
  - ⏳ не начато;
  - ➡️ перенесено в пункт X.Y.
- **Ссылки на код** — пути от корня репозитория. Можно указать в шапке общую базу, например `backend/src/aiskra/`. Тесты — `файл::функция`.
- **«Проверено»** — только автотест или воспроизводимая команда. Ручная проверка помечается как «вручную» с описанием.
- **Коммиты:** в теле коммита — строка `Refs: 0.2 (R0.2-09, R0.2-10)`, заголовок — по [docs/rules/git.md](../docs/rules/git.md). Тогда `git log --grep 'R0.2-09'` находит коммиты по требованию.
