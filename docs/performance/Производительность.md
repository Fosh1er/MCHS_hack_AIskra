# Производительность и устойчивость (п. 6.1)

Для раздела «Условия и ограничения» сопроводительной документации. Трассировка — [specs/6.1-performance.md](../../specs/6.1-performance.md).

## 1. Требования ТЗ и результат
Замер 26.09.2026, один процесс API (как в `docker compose`), SQLite, MacBook (Apple Silicon). База — примерно год работы учебного центра: 76 тыс. карточек, 173 тыс. строк служб, 235 тыс. записей аудита.

| Требование ТЗ | Цель | Результат | |
|---|---|---|---|
| Отклик интерфейса при 100 пользователях | ≤ 2 с | p95 — 16 мс, p99 ≤ 0,6 с, максимум 0,94 с | ✅ |
| Одновременных сессий (вызов → карточка → ДДС) | ≥ 20 | 20 активных + 80 просматривающих, 0 ошибок за 2 минуты | ✅ |
| Запись в БД | ≥ 100 оп/с | 253 карточки в секунду (карточка + запись аудита), 20 писателей | ✅ |
| Отчёт по занятию | ≤ 30 с | «оценить все» + отчёт по 729 карточкам — 4,1 с | ✅ |
| Сбой связи до 30 с без потери работы | — | черновик карточки в браузере, повтор отправки, приложение оживает само | ✅ |

## 2. Методика
`backend/tools/loadtest.py`: 100 учёток входят по 20 одновременно; 20 из них ведут полный цикл — учебный вызов, три реплики ИИ-заявителю, автоподбор служб, сохранение карточки, приём и статус ДДС; 80 — журналы 112 и ДДС, карточки, справочники, подсказка адреса с паузами 1–3 с «на чтение». Затем 15 с записи двадцатью писателями и отчёт по занятию. Объём данных — `backend/tools/bulk_seed.py`.

```bash
AISKRA_DEMO_PASSWORD='…' uv run python -m aiskra.cli demo-seed --load-users 100
uv run python tools/bulk_seed.py --cards 50000 --audit 200000      # объём, только для стенда нагрузки
AISKRA_DEMO_PASSWORD='…' uv run python tools/loadtest.py --base https://сервер:8443 --duration 120
```
Результаты — JSON рядом с этим документом.

## 3. Что нашёл замер и что исправлено
На пустой базе всё было быстро; на объёме года — p95 1,6 с, p99 до 5 с: единственный процесс API стоял в очереди за тяжёлыми запросами журналов.

| Было | Причина | Исправление | Стало |
|---|---|---|---|
| журнал ДДС 122 мс на запрос | подсчёт и сортировка по 18 тыс. карточек службы с подзапросом «время статуса» по каждой | время сохранения и номер карточки копируются в строку службы; подсчёт и страница — по одному индексу; полные строки и время статуса — только для 10 строк страницы | 5 мс |
| журнал 112: подсчёт считал статус «Не оповещено» по всем строкам | подсчёт оборачивал запрос страницы | подсчёт без вычисляемого статуса | 4 мс |
| статус «Не оповещено» | **ошибка**: подзапрос не был связан с карточкой — отработка службы в одной карточке «оповещала» все карточки с этой службой | корреляция с нужной строкой; регрессионный тест | верно |
| сортировка журнала 112 по выражению | индекс по выражению не используется | «дата регистрации» — `opened_at`, пустые заполнены миграцией | по индексу |
| — | нет индексов под журналы, историю статусов, отработки, оценки | миграция 0011: 8 составных индексов | — |

Итог — таблица в §1: p95 с 1556 до 16 мс при вдвое большем потоке запросов.

## 4. Устойчивость
- **Черновик карточки 112** — в `localStorage` браузера каждые 0,5 с; после перезагрузки или сбоя карточка открывается с сообщением «Восстановлен черновик»; удаляется после сохранения.
- **Сохранение переживает обрыв:** при сетевой ошибке или ответе прокси (502/503/504) отправка повторяется каждые 3 с в течение минуты. Если сервер успел сохранить, а ответ потерялся, повтор получит «уже сохранена» — это считается успехом.
- **«Нет связи с сервером»** — баннер появляется за 1–2 с после сбоя и пропадает сам; журналы и сессия восстанавливаются без перезагрузки, в том числе если страницу перезагрузили во время сбоя.
- **Фоновое окно.** По умолчанию библиотека запросов не опрашивает сервер и не повторяет запросы, пока окно без фокуса, — диспетчер ДДС с окном в фоне пропустил бы новую карточку и сигнал. Журналы опрашиваются и в фоне.
- WebSocket не используется (опрос раз в 5 с, ADR-0005), поэтому «переподключение» — это повтор запросов и восстановление сессии.

## 5. Кеш и объём трафика
- Справочники кешируются браузером на 10 минут (`Cache-Control: private, max-age=600`) и на время работы вкладки (TanStack Query); остальной API — `no-store`.
- Ответы больше 1 КБ сжимаются (gzip в API и в nginx): границы районов 175 КБ, справочник служб 73 КБ.
- Серверный кеш справочников не понадобился: они отвечают за 2–6 мс.

## 6. Ограничения замера
- Замер на SQLite (на машине разработки нет PostgreSQL и Docker). SQLite — худший случай для одновременной записи (один писатель); на PostgreSQL запись и подсчёты быстрее. Тот же скрипт повторяется на сервере в M7.
- ИИ в офлайн-режиме. С локальной моделью время ответа заявителя определяется моделью (на CPU без GPU — секунды); это ответ собеседника, а не отклик интерфейса, и от нагрузки на API он не зависит.
- Поиск по тексту в журнале ДДС (`LIKE '%…%'`) — около 100 мс на 18 тыс. карточек службы; для PostgreSQL — индекс `pg_trgm`, если понадобится.
