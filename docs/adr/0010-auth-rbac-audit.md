# 0010. Вход, права и аудит: серверные сессии в cookie, матрица прав в общем ядре, аудит через порт

- **Статус:** Принято
- **Дата:** 2026-09-26
- **Пункты плана:** 0.3 (дальше используется всеми пунктами), 5.2

## Контекст
- **ТЗ «Роли», «Безопасность»:**
  - три роли;
  - аутентификация при каждом входе;
  - RBAC и защита от НСД;
  - аудит всех действий, хранение журналов безопасности не меньше 6 месяцев;
  - TLS внутри контура.
- **Ограничения ролей:** администратор не меняет оценки и сценарии, у преподавателя нет админ-функций, обучающийся не видит чужого.
- **Оригинал АРМ-112:**
  - вход по логину, паролю и номеру АРМ (`image1.png`), автовыход через 24 ч;
  - раздел «Аудит» с колонками Карточка, Опер., ФИО, Дата, Время, Событие, Описание (`image114.png`).
- **Изолированный контур:** внешних IdP нет; LDAP — опционально (ТЗ 10.7).
- **Развёртывание:** фронтенд и API отдаются с одного адреса через nginx.
- **Независимость модулей (ADR-0001):** аудит нужен всем модулям, но модуль `audit` импортировать нельзя.

## Решение
**Сессии — на сервере, токен — в cookie.**
- Вход (`POST /api/v1/auth/login`) создаёт запись в `auth_sessions`.
- Клиенту уходит случайный токен (256 бит) в cookie `aiskra_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` — в контуре с TLS (`AISKRA_SESSION_COOKIE_SECURE`).
- В БД хранится только SHA-256 токена.
- Срок жизни — 24 ч, как в оригинале (`AISKRA_SESSION_TTL_HOURS`).
- На каждом запросе пользователь, его роль и статус читаются из БД. Поэтому блокировка и смена роли действуют сразу, а выход и блокировка отзывают сессию на сервере.
- JWT не используем: его нельзя отозвать без списка отзыва, а выигрыш в производительности при нагрузке ТЗ несущественный.

**Пароли — scrypt из стандартной библиотеки (RFC 7914)**, без внешних зависимостей.
- Параметры хранятся внутри хеша (`scrypt$n$r$p$соль$ключ`), чтобы их можно было усилить позже.
- Хеш считается в потоке и не блокирует event loop.

**Защита от подбора.**
- После 5 неудачных попыток подряд вход закрыт на 15 минут (`AISKRA_LOGIN_*`).
- Для несуществующего логина выполняется «пустой» расчёт хеша: время ответа не выдаёт, есть ли такой логин.
- Сообщение об ошибке одинаковое: «Неверный логин или пароль».

**Номер АРМ.**
- Вводится при входе (1–6 цифр, необязательный).
- Хранится в сессии; попадает в аудит и понадобится для колонки «АРМ» журнала происшествий.

**Роли и права — в общем ядре** (`aiskra/shared/security.py`).
- `Role` и `Permission`, матрица `ROLE_PERMISSIONS` по ТЗ. Модули проверяют право, а не роль.
- HTTP-часть — `aiskra/shared/web.py`:
  - `CurrentPrincipal` → 401;
  - `require(Permission.X)` → 403 и запись «Отказ в доступе» в аудит.
- **Запрет по умолчанию:** в `main.py` все роутеры `/api/v1`, кроме `/auth`, подключены с обязательной сессией. Тест обходит все маршруты из OpenAPI-схемы без входа и ждёт 401.

**Аудит — порт в общем ядре** (`aiskra/shared/audit.py`: `AuditRecorder`, `AuditEntry`, каталог `AuditEvent`).
- Обработчик команды пишет событие явно (ADR-0002), в той же транзакции, что и изменение.
- Неудачный вход фиксирует попытку и счётчик до ответа ошибкой.
- Отказ в доступе пишется отдельной короткой транзакцией: запрос всё равно завершится ошибкой.
- Реализации лежат в `modules/audit/infrastructure`. Журнал только дополняется: API изменения и удаления нет.

**Поиск без учёта регистра.** Ключи поиска (`users.search_key`, `audit_log.actor_key`, `description_key`) нормализуются в Python: регистр, ё→е. `lower()` в PostgreSQL зависит от локали базы (в локали `C` кириллица не понижается), а в SQLite работает только для ASCII.

**Начальный администратор.**
- `python -m aiskra.cli ensure-admin` запускается при старте контейнера. Если в окружении задан пароль (`AISKRA_BOOTSTRAP_ADMIN_PASSWORD`), команда создаёт администратора; повторный запуск ничего не меняет.
- Остальные пользователи создаются через API или `cli create-user`.
- Паролей в репозитории нет.

## Последствия
- **Плюсы:**
  - мгновенный отзыв доступа;
  - нет CORS и хранения токена в JS;
  - WebSocket (1.4, 2.x) аутентифицируется той же cookie;
  - новые эндпоинты защищены по умолчанию.
- **Минус:** один запрос к БД на каждый защищённый запрос (выборка по уникальному индексу). При росте нагрузки добавляется кеш сессий на несколько секунд, интерфейс не меняется.
- **CSRF:** закрывается `SameSite=Strict` и JSON-телом запросов — форма с другого сайта не отправит cookie и не пройдёт CORS-предзапрос.
- **Не сделано** (открытые вопросы в спецификации 0.3):
  - второй фактор (TOTP) для администратора и преподавателя;
  - LDAP/AD;
  - автоматическая очистка журнала старше срока хранения.
- **Откат:** замена способа сессии затрагивает `identity` и заглушку `provide_principal`, остальные модули не меняются.
