# 0014. Ветвящиеся сценарии: граф ситуации в шаблоне, путь — функция фактов звонка

- **Статус:** Принято
- **Дата:** 2026-10-19
- **Пункты плана:** F5 (бэклог финала), связь с 3.3, 3.6, 3.7, F1

## Контекст
Раньше легенда сценария была неподвижной: что бы ни делал оператор 112, заявитель рассказывал одно и то же, а оценка сравнивала карточку с эталоном. Для тренажёра МЧС этого мало. Результат работы оператора — то, что произошло с людьми, пока ехала помощь:
- быстро ли получен адрес и ушла ли карточка нужной службе (ПП РФ № 1931: карточка доступна ДДС в среднем через 75 с);
- какую инструкцию оператор дал заявителю по официальной памятке;
- не дал ли он вредного совета («откройте окна» при пожаре, «вытащите его из машины» при ДТП).

Ограничения:
- **итог объясним:** преподаватель должен показать, какая развилка к нему привела и что было бы при другом решении, со ссылкой на источник;
- **итог воспроизводим:** те же решения дают тот же итог, а оценка не зависит от модели;
- **совместимость:** существующие сценарии, психологический модификатор (ADR-0012) и поток ответа (ADR-0013) работают как раньше;
- **без модели:** тренажёр работает и без ключа;
- **источники:** только официальные.

## Решение
- **Граф — в YAML-шаблоне, а не у модели.**
  - Шаблоны лежат в `data/dictionaries/branch_templates.yaml`. Сейчас их четыре: пожар в квартире, остановка дыхания и сердца, запах газа, ДТП с пострадавшими.
  - Узел описывает: что происходит сейчас, факты поверх легенды, ворота (что заявитель может сообщить), реплику-событие, сдвиг состояния заявителя, доклад старшего группы по статусам ДДС и итог для конечного узла.
  - У каждого перехода и инструкции есть источник из реестра `sources`. Шаблон содержит контрольные ходы: идеальный оператор, типичная ошибка, худший случай.
  - Каталог проверяется при старте и в CI (`validate_graph`):
    - все узлы достижимы, на каждом пути есть итог;
    - у каждого неконечного узла есть переход только по времени, поэтому ситуация не застывает, если оператор молчит;
    - цикл возможен только через такой переход.
- **Сценарий хранит снимок.** При генерации шаблон с подставленной легендой копируется в `scenarios.branching` (миграция 0020) вместе с использованными источниками. Правка каталога не меняет утверждённые сценарии и прошедшие звонки.
- **Модель только переписывает формулировки.** Новая ИИ-задача `branch_texts` переписывает реплики-события под легенду. `check_event_text` отклоняет ответ, если в нём появились числа, номера служб или ремарки, которых не было. Структуру графа, условия и итоги задаёт только шаблон.
- **Путь — чистая функция фактов с отметками времени.**
  - В `training_calls.branch` хранится, что и когда случилось:
    - `said` — какие инструкции оператор сказал и когда; распознаются по основам слов, у вредных советов отсекается отрицание;
    - `asked` — что сообщил заявитель;
    - `acts` — действия по модификатору.

    Там же — текущий узел и путь.
  - Факты карточки (когда сохранена, с какими службами, статусы ДДС) приходят через порт `CardContextSource.card_timeline`.
  - `resolve(шаблон, факты, до_момента)` проходит все пороги времени и моменты фактов по порядку. Шаг по ходу звонка и пересчёт целиком дают один и тот же путь (проверено тестом).
  - Итог в оценке, разборе и докладе бригады считается одной функцией, поэтому они не расходятся.
- **Условия перехода** складываются через «и»; срабатывает первый подходящий переход по порядку:
  - `said` / `asked` / `act` — решение оператора;
  - `after_s` — время от ответа на вызов;
  - `card_by_s` + `service` — карточка сохранена вовремя и с нужной службой;
  - `dds` — статус службы;
  - `ended` — разговор завершён.

  Переходы только по времени — учебное упрощение. Они помечены `note: didactic` и в разборе подписаны «время учебное».
- **Когда делается шаг:**
  - на каждой реплике оператора, до ответа заявителя и рядом с шагом профиля;
  - по таймеру: `POST /training/calls/{id}/tick` раз в 5 с, пока звонок идёт; при занятом звонке тик возвращает пустой ответ;
  - при каждом пересчёте итога.
- **Узел меняет заявителя, а не модель — состояние:**
  - что происходит сейчас уходит в промпт `applicant_actor/v4`; у профиля этот блок дописывается к `v3`;
  - факты узла дополняют легенду;
  - ворота узла объединяются с воротами профиля;
  - `escalate` сдвигает `CallerTone` (причина `situation`) или уровень ECCS профиля;
  - реплика-событие звучит один раз — в начале ответа или сообщением тика.
- **Оценка.**
  - Блок `details.branch`: итог `favorable / partial / adverse / tragic` даёт 100 / 60 / 30 / 0 баллов.
  - Вес блока — `settings.branch.weight` занятия, снимок хранится в звонке. По умолчанию вес 0, и блок только информирует.
  - Сложение с баллом роли — та же функция `combine()`, что у профиля.
  - Итог окончательный, когда разговор завершён и карточка сохранена.
- **Выключено — ничего не меняется.** Все новые ветки срабатывают только при `call.branch`. Сценарий без шаблона ведёт себя как раньше.

## Последствия
- **Плюсы:**
  - разное решение даёт разный итог уже за один звонок короче 3 минут;
  - разбор «вы / иначе» со ссылками строится из того же графа, по которому шла ситуация;
  - итог детерминирован и не зависит от модели; бенчмарк мутаций доказывает, что каждая развилка достижима и меняет итог;
  - работает без ключа.
- **Минусы:**
  - распознавание инструкций по основам слов пропускает перефразировки. Словарь шаблона придётся расширять по стенограммам;
  - пороги времени — учебные, а не нормативы. Это сказано в разборе;
  - путь меняет доклад старшего группы, но не набор статусов ДДС: запроса дополнительных сил в АРМ ДДС нет;
  - тики и блокировка звонка живут в памяти процесса (как в ADR-0013). Для нескольких копий backend их нужно перенести в БД.
- **Что дальше:** редактор графа для преподавателя, импорт и экспорт YAML (RF5-10, P2); условия по событиям ДДС в шаблонах занятий 112 + ДДС.
- **Откат:** не выбирать шаблон при генерации. Сценарии без `branching` работают по-старому, а колонки миграции 0020 допускают `NULL`.
