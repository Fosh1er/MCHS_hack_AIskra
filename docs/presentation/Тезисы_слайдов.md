## До обязательных слайдов (1–6)

### 1. Титул
**АИскра** — ИИ-тренажёр операторов системы-112 и диспетчеров ДДС. ЛЦТ 2026, задача № 9, ДГОЧСиПБ Москвы.

### 2. Проблема
- **Оператор 112** за 75 с должен опросить заявителя, заполнить карточку по классификатору (1281 тип, 24 группы) и назначить службы. Норматив — ПП РФ № 1931.
- **Диспетчер ДДС** должен подтвердить приём карточки за 30 с.
- **Реальных вызовов для учёбы нет.** Учебные вводные преподаватель пишет вручную. Их мало, и они быстро запоминаются.
- **Карточки проверяются вручную:** долго, субъективно, без статистики по типичным ошибкам и без данных для допуска к дежурству.

### 3. Решение
- **Копия АРМ-112 и АРМ ДДС:** та же карточка, журнал, статусы служб и справочники заказчика.
- **ИИ генерирует сценарии вместе с эталоном:** легенду заявителя, правильную карточку и правильные действия ДДС.
- **ИИ-заявитель и ИИ-старший группы в учебном звонке** отвечают только тем, что есть в легенде.
- **Автооценка** каждой карточки и работы ДДС по эталону. Аналитика для преподавателя и оценка готовности к допуску.
- **Работает в изолированном контуре:** на локальной модели или в офлайн-режиме без модели.
- *Скриншоты:* `02_card112_call.png`, `13_dds_card.png`.

### 4. Демо-сценарий: две роли в одном занятии
1. Преподаватель запускает смешанное занятие.
2. Оператор 112 принимает учебный вызов, опрашивает ИИ-заявителя, заполняет карточку. Службы подбираются по матрице классификатора.
3. Карточка уходит в очередь ДДС нужной службы.
4. Диспетчер принимает её, ведёт статусы до «Работы завершены», звонит старшему группы.
5. Преподаватель видит всё на мониторинге, после занятия получает отчёт и разбор.

*Скриншоты:* `01_arm112_journal.png` → `02_card112_call.png` → `12_dds_journal.png` → `13_dds_card.png` → `04_monitor.png`.

### 5. Архитектура
- **Стек:** модульный монолит на FastAPI (чистая архитектура, CQRS-lite), React SPA, PostgreSQL 16, nginx с TLS. Весь стенд поднимается одной командой `docker compose up`.
- **ИИ за портами:** задачи (генерация, заявитель, старший группы, судья) назначаются моделям в `config/ai.yaml`. Подходит Ollama, vLLM, llama.cpp или любой OpenAI-совместимый сервер.
- **API:** REST, 103 операции, описание OpenAPI. Роли и права проверяются на каждом запросе, все действия пишутся в журнал аудита.
- *Схема:* `docs/architecture/overview.md`.

### 6. ИИ и достоверность оценки
- **Эталон согласован с легендой:** он строится вместе с ней из тех же признаков.
- **Автооценка — детерминированные критерии с весами:**
  - карточка 112: тип — 3, службы — 2, адрес — 2 и остальные;
  - работа ДДС: решение — 3, время — 2, статусы — 2 и остальные.

  Балл от 0 до 100, «зачтено» — от 70. ИИ-судья проверяет только смысл и грамотность описания.
- **Экспертная правка** преподавателя сохраняется. На этих данных методика сверки: средняя абсолютная ошибка балла (MAE) и согласие «зачтено / нет» (κ Коэна). Расчёт на экспертной выборке заказчика — следующий шаг. Честно: чисел пока нет.

## После обязательных (12–18)

### 12. Преподаватель: занятия и отчёт
- **Банк сценариев:** генерация, прогон, утверждение.
- **Занятие:** тип, категории, роли, нормативы и темп.
- **Мониторинг** в реальном времени.
- **Отчёт:** тепловая карта «обучающийся × критерий», время против норматива, экспертная правка, выгрузка в Excel и PDF.
- *Скриншоты:* `05_scenario_bank.png`, `04_monitor.png`, `06_report.png`.

### 13. Аналитика по практике подготовки персонала 112 и ЕДДС
- **«Норматив / факт»** по образцу формы 1/112 (приказ МЧС № 192): доля в нормативе, медиана, 90-й процентиль.
- **Профиль обучающегося:** критерии против группы, типичные ошибки, отработанные группы классификатора.
- **Разбор занятия** для подведения итогов смены (ГОСТ Р 22.7.01).
- **Подбор задания по слабым местам** — одной кнопкой.
- *Скриншоты:* `08_analytics.png`, `09_student_profile.png`, `07_debrief.png`, `11_assignment.png`.

### 14. Готовность к допуску
- **Шкала итогового контроля** Программы подготовки ЕДДС (МЧС, 2023): 90 / 75 / 60 % с учётом укладывания в норматив. Считается по последним 10 карточкам.
- **Заключение:** «готов к зачёту» или «нужна дополнительная практика». Во втором случае одной кнопкой назначается индивидуальное задание.
- **Протокол** для печати с подписями (профстандарт 12.002, функция C/03).
- *Скриншот:* `10_readiness.png`.

### 15. Соответствие ТЗ
Из обязательных требований (M) полностью реализовано 47 из 48. Подчинённость объектов (4.4): механизм готов, включается, когда заказчик передаст справочник. Полная матрица — в пояснительной записке.

### 16. Производительность
Замер: 100 пользователей, объём данных примерно за год работы.
- **Отклик:** 95-й процентиль — 16 мс при требовании не более 2 с.
- **20 активных сессий** одновременно.
- **Запись:** 253 карточки в секунду при требовании не менее 100.
- **Отчёт по занятию:** 4,1 с при требовании не более 30 с.
- **Обрыв связи:** черновик карточки сохраняется, сохранение повторяется автоматически.

### 17. Внедрение в локальный контур
1. Сервер по ТЗ: 6 ядер, 32 ГБ, без GPU.
2. `docker compose up`.
3. Импорт справочников заказчика из панели администратора.
4. Локальная модель (профиль `local-llm`).
5. Учётные записи и группы.
6. Резервные копии.

Внешние сети не нужны.
