## F1. Генерация токенов в реальном времени

### 1.1 Цель
Ответ ИИ-собеседника появляется на экране по мере генерации: курсор, токены, метрики скорости. Озвучка начинается с первой фразы, а не после всего ответа. Это одновременно и демонстрация генеративной природы решения, и реальное ускорение: в задаче R3.6-31 первая фраза должна звучать меньше чем через 1,5 с после конца речи оператора.

### 1.2 Что есть сейчас
- `POST /training/calls/{id}/replicas` отдаёт ответ целиком (`SendReplicaHandler`, `training/application/commands/calls.py`).
- `LLMPort.complete` без стриминга (`ai/ports.py`). Адаптер `OpenAICompatibleLLM` шлёт запрос без `stream` (`ai/adapters/openai_compatible.py`).
- Кэш ответов — `ai/adapters/caching.py`, режимы `exact|task|off`.
- Ветка с психологическим профилем `_psy_reply`:
  - ответ модели проверяет `psy_render.validate`;
  - при отказе подставляется `offline_reply`;
  - ремарки `[плачет]` разбирает `parse_remarks`.
- Голосовой полигон уже отдаёт SSE в формате OpenAI, но это поток фраз из готового ответа (`api/router.py:voice_lab_chat`).
- Фронт — `shared/ui/CallPanel.tsx`: реплика добавляется в `messages` целиком; озвучка — по `message_id`.

### 1.3 Требования
| ID | Требование |
|---|---|
| RF1-01 | `LLMPort.stream(messages, params) -> AsyncIterator[LLMDelta]`. Реализации: OpenAI-совместимый адаптер (`stream: true`, разбор SSE `data:`), `fake` (слова с задержкой 30–60 мс), кэш (см. RF1-08). `complete()` остаётся, работает через `stream()` или как сейчас |
| RF1-02 | Эндпоинт `POST /training/calls/{id}/replicas/stream` (SSE). События по порядку: `accepted` → `state`* → `token`* → `sentence`* → (`replace`)? → `final` \| `error`. Старый эндпоинт остаётся для тестов, отката и офлайна |
| RF1-03 | `state` — до генерации: детерминированный шаг состояния (CallerTone / ECCS профиля) известен заранее; плашка изменения состояния появляется сразу, а не после ответа |
| RF1-04 | Ремарки в квадратных скобках не печатаются потоком посимвольно: фильтр буферизует от `[` до `]` и отдаёт ремарку отдельным событием `remark` |
| RF1-05 | Проверка ответа (`validate`) — по готовому тексту. При отказе — событие `replace {text, reason}`: фронт плавно заменяет текст (без мигания), в разборе преподавателя видна причина. Озвучка заменённого ответа идёт по новому тексту |
| RF1-06 | `sentence` — граница фразы (`.!?…` + пробел, или 120 символов). Фронт озвучивает фразы очередью: `POST /training/calls/{id}/speech {text, idx}` → аудио, голос и стиль — как у реплики (роль, `VoiceProfile.style` из состояния) |
| RF1-07 | Перебивание: оператор начал говорить (VAD) или нажал «стоп» → фронт закрывает поток (`AbortController`), сервер ловит отключение. Сохраняется сказанное до этого момента с `meta.interrupted = true`; сигнал `INTERRUPT` уходит в модификатор (уже есть в `TurnSignals`) |
| RF1-08 | Кэш: при попадании ответ отдаётся тем же потоком с имитацией темпа и пометкой `cached` в `final` (метрики честные). При промахе текст собирается и кладётся в кэш после `final` |
| RF1-09 | Сохранение в БД — одной транзакцией после `final` (реплика оператора + ответ + состояние). Генератор SSE работает со своей сессией или UoW: сессия из `Depends` закрывается раньше, чем завершается `StreamingResponse` |
| RF1-10 | Метрики каждой реплики в `training_call_messages.meta.ai`: `ttft_ms`, `total_ms`, `tokens`, `tok_s`, `model`, `cached`, `replaced`. На странице «ИИ-модели» (`/dev/ai`) — p50 и p95 за сутки по задаче |
| RF1-11 | UI в `CallPanel`: курсор-каретка, плавное проявление токенов, индикатор «ИИ генерирует · 38 ток/с · первый токен 420 мс · модель». Индикатор включается в настройках занятия («показывать работу ИИ») и всегда включён на демо-стенде (F2). В офлайн-режиме подпись честная: «ответ по правилам», без имитации модели |
| RF1-12 | Разговор без рук (V3): очередь фраз, отсев эха `isLikelyEcho` и перебивание работают с потоковыми фразами |
| RF1-13 | Голосовой полигон (`/voice-lab`) переходит на настоящий поток через `LLMPort.stream` |
| RF1-14 | nginx: для `/api/v1/training/calls/*/replicas/stream` и `/voice-lab/chat` — `proxy_buffering off`, `X-Accel-Buffering: no`, `proxy_read_timeout 120s` |
| RF1-15 | Ошибка модели посреди потока → `error`, затем офлайн-ответ событием `replace`. Звонок не ломается |

### 1.4 Дизайн
- **Порт:** `LLMDelta(text: str, done: bool, usage: LLMUsage | None)`. `TaskModel.stream()` в `ai/router.py` по аналогии с `complete()`, с теми же `LLMParams`, кэшем и `prompt_version`.
- **Прикладной слой:**
  - `StreamReplicaHandler` в `calls.py` повторяет `SendReplicaHandler`, но возвращает асинхронный итератор доменных событий `ReplicaEvent` (без HTTP);
  - API превращает события в SSE;
  - общий код `_reply` и `_psy_reply` выносится, чтобы не держать две копии логики.
- **Психологический профиль:**
  - `PsyDirector.turn` делится на два шага: `prepare()` (классификация актов, шаг движка, ворота, промпт — всё детерминированно) и `finish(text)` (проверка, офлайн-замена, разметка);
  - между шагами идёт поток модели.
- **Фронт:**
  - новый хук `useReplicaStream(callId)` (fetch + `ReadableStream`, без EventSource: нужен POST);
  - `TranscriptMessage` получает `streaming: boolean`, анимация — в ui-kit (`arm.css`);
  - озвучка — очередь `sentence`, `stopVoice()` прерывает и очередь, и поток.

### 1.5 Файлы
- **Порты и адаптеры ИИ:** `ai/ports.py`, `ai/router.py`, `ai/adapters/openai_compatible.py`, `ai/adapters/fake.py`, `ai/adapters/caching.py`.
- **Прикладной слой:** `training/application/commands/calls.py`, `training/application/psy.py`, `training/application/actors.py`.
- **API:** `training/api/router.py` (`/replicas/stream`, `/speech`), `training/api/schemas`.
- **Инфраструктура:** `infra/nginx/templates/default.conf.template`.
- **Фронтенд:** `frontend/src/shared/ui/CallPanel.tsx`, `shared/api/training.ts`, `packages/ui-kit` (Transcript), `frontend/public/voice-lab/app.js`.
- **Документы:** ADR-0013, `specs/F1-streaming.md`, обновить R3.6-31 в `specs/3.6-emotional-voice.md`.

### 1.6 Тесты
- **Unit:**
  - разбор SSE адаптером: `httpx.MockTransport`, порванные чанки, `[DONE]`, ошибка посреди потока;
  - фильтр ремарок;
  - нарезка фраз;
  - кэш: replay при попадании и запись при промахе.
- **Integration:**
  - последовательность событий для обычного звонка и звонка с профилем;
  - `replace` при стоп-слове;
  - обрыв клиента → сохранено частичное + `interrupted`;
  - права: чужой звонок → 403/404.
- **E2E (Playwright):** текст появляется частями, озвучка начинается до `final` (fake TTS).
- **Регресс:** бенчмарк мутаций `unit/test_psy.py` зелёный без изменений.

### 1.7 Приёмка
- [ ] На демо-модели p50 первого токена ≤ 1,0 с, первая озвученная фраза ≤ 1,5 с после отправки реплики (замер на стенде, 30 реплик).
- [ ] Перебивание останавливает и звук, и генерацию ≤ 300 мс.
- [ ] Отказ модели посреди ответа не ломает звонок.
- [ ] Офлайн-режим работает, подпись честная.

### 1.8 Риски
- Буферизация в прокси: nginx и cloudflared могут копить поток — проверить на стенде, не только локально.
- Бесплатные модели OpenRouter держат запрос в очереди. Решение — F3.
- Длина транзакции при обрыве: сохраняем только после `final` или обрыва, без промежуточных записей.

## F3. Подбор моделей LLM, TTS и STT под быстрые ответы

### 3.1 Цель
Выбор моделей по замерам, а не по названию. Для каждой ИИ-задачи — лучшая модель по критериям «скорость / качество / стоимость», отдельно для демо-стенда (внешний API) и для контура заказчика (CPU, без GPU).

### 3.2 Задачи и критерии
| Задача (`AITask`) | Что важно | Порог |
|---|---|---|
| `applicant_actor`, `brigade_actor`, `service_actor` | первый токен, русская разговорная речь, удержание роли, краткость | p50 первого токена ≤ 0,8 с; доля ответов, прошедших `validate`, ≥ 95 %; выход из роли ≤ 1 % |
| `psy_acts` | JSON-классификация, скорость | валидный JSON ≥ 99 %; p50 ≤ 0,7 с; согласие с офлайн-классификатором на эталоне ≥ 85 % |
| `judge`, `psy_judge` | точность, стабильность, JSON | κ с эталонной разметкой ≥ 0,6; валидный JSON ≥ 99 % |
| `scenario_generation`, `feedback_draft` | качество текста, факты легенды не нарушены | 0 нарушений фактов на 30 сценариях |
| TTS (голос заявителя) | время до первого звука, эмоция, русская речь | до первого звука ≤ 600 мс на фразу ≤ 120 символов; слепая оценка эмоции ≥ 4/5 |
| STT (оператор) | точность на адресах и номерах, задержка | WER ≤ 12 % на тестовом наборе, адреса ≤ 5 % ошибок; ≤ 1,2 с на фразу 5 с |

### 3.3 Метод
- **Инструмент `backend/tools/bench_models.py`:**
  - вход — файл кандидатов `config/bench/candidates.yaml`, фиксированный набор: 30 сценариев × 6 реплик оператора, включая провокации для психологического профиля;
  - для LLM — замеры первого токена, полного ответа, ток/с, отказов `validate`, выхода из роли, стоимости 1000 звонков;
  - для TTS — 20 фраз × 4 эмоции;
  - для STT — 50 фраз: синтез разными голосами + 20 живых записей команды; набор лежит в `data/bench/`, ПДн нет.
- **Отчёт:** `docs/validation/models_<дата>.md` — таблица, медианы, p95, выбранная модель по задаче и обоснование.
- **Слепая оценка голоса:** 3 человека, шкала 1–5 по естественности и соответствию эмоции; файлы перемешаны, без названий моделей.
- **Конфиги:**
  - `config/ai.openrouter.yaml` → выбранные модели;
  - новый `config/ai.demo-fast.yaml`: платный быстрый тариф для питча, лимит на ключе;
  - `config/ai.local.yaml` — контур заказчика.

### 3.4 Кандидаты
Список уточняется по каталогу провайдера в день замера: модели и цены меняются.
- **Сейчас в репозитории:**
  - LLM на демо — `nvidia/nemotron-3-super-120b-a12b:free`; бесплатные модели с очередью — риск для питча;
  - LLM в прототипе полигона — `google/gemini-3.1-flash-lite`;
  - TTS — `google/gemini-3.8-flash-lite-tts`;
  - STT — `openai/whisper-large-v3-turbo`;
  - контур без GPU — Qwen2.5 7B/3B Instruct (Ollama), Piper, faster-whisper.
- **Что добавить в замер:**
  - 2–3 быстрые «lite/flash»-модели разных провайдеров с поддержкой стриминга и JSON;
  - 1 сильная модель для `judge` и `scenario_generation` (там скорость не критична);
  - TTS с потоковым PCM;
  - для контура — квантованные 3–8B модели на CPU (замер первого токена на 6 ядрах).

### 3.5 Приёмка
- [ ] Отчёт бенчмарка в репозитории, на каждую задачу — выбранная модель и цифры.
- [ ] Демо-конфиг переключён, на стенде достигнуты пороги задачи `applicant_actor`.
- [ ] Расходы демо-ключа ограничены лимитом, ключ выпущен заново: старый был в переписке.

## F4. Психологический профиль — на первый план

### 4.1 Цель
Эксперт с первого экрана видит, что модификатор построен на официальной методике, а не на «промпте про эмоции». Каждое правило прослеживается до источника.

> **Ограничение по формулировкам.** Писать «разработано психологами МГУ», ставить логотипы вузов или ФИО экспертов можно только при подтверждённом участии конкретного специалиста и его письменном согласии. Иначе на защите это первый вопрос и потеря доверия. Сильная честная формулировка: «методика по пособиям ЦЭПП МЧС России, профстандарту 12.002 (приказ Минтруда № 681н), шкале ECCS IAED; ≈100 проверенных источников». Если удастся получить рецензию практикующего психолога ЦЭПП или кафедры — добавить блок «Рецензия» с его согласия.

### 4.2 Требования
| ID | Требование |
|---|---|
| RF4-01 | В звонке с профилем: панель «Состояние заявителя» в `CallPanel` — шкала ECCS 1–5 в реальном времени, стадия, доверие. Рядом с каждым изменением — причина из `ACT_TITLES` («обесценивание: "успокойтесь"») и значок «источник», по клику — цитата и ссылка (`psy_profiles.yaml: sources`) |
| RF4-02 | Блок оценки «Работа с заявителем в стрессе» (`PsyBlock.tsx`): у каждого критерия — источник (пособие ЦЭПП, профстандарт 12.002, функция C/04.6 и т. п.) и короткое «почему это важно». Данные уже есть в `psy_scoring.WHY` — вывести в интерфейс |
| RF4-03 | Страница «Методика» (`/teacher/methodology` и вкладка в справочной базе обучающегося): 15 профилей карточками — признаки, что делать, что нельзя, источники. Генерируется из `psy_profiles.yaml` и `docs/research/psychology/`, без ручной копии текста |
| RF4-04 | Банк сценариев и занятия: бейдж профиля на сценарии, фильтр «с психологическим профилем», счётчик профилей в занятии |

## F5. Ветвящиеся сценарии

### 5.1 Цель
Ситуация развивается по решениям оператора и диспетчера.
- Не спросил адрес вовремя — огонь перекинулся на соседнюю квартиру.
- Дал инструкцию «закройте дверь, не пользуйтесь лифтом» — люди эвакуировались.
- Не отправил скорую при признаках остановки дыхания — исход трагический.

Итог виден в конце звонка и в разборе: какая развилка к нему привела и что было бы при другом решении.

### 5.2 Модель
- **Узел ситуации (`node`):**
  - описание для модели (что сейчас происходит);
  - изменения легенды (`facts` поверх легенды сценария);
  - открытые ворота (что заявитель может сообщить);
  - реплика-событие заявителя при входе в узел («Дым уже в коридоре!»);
  - события для движка профиля (F4-07);
  - итог, если узел конечный.
- **Переход (`edge`):** условие → целевой узел. Условия:
  - действие оператора: коды актов модификатора (`psy_acts`) и темы опроса (`topic_of`);
  - время: «нет адреса через 60 с от ответа»;
  - событие карточки: служба отправлена, инструкция дана, карточка сохранена;
  - событие ДДС: «Принята» за N с, бригада на месте.
- **Итог (`outcome`):**
  - код `favorable | partial | adverse | tragic`;
  - текст;
  - норматив и источник, например «время доезда — ПП РФ № 1931», «инструкция при пожаре — памятка МЧС».
- **Хранение:**
  - `scenarios.branching` (JSON, миграция 0020) — копия шаблона с параметрами сценария;
  - `training_calls.branch` — текущий узел и путь с отметками времени.
- **Шаблоны:** `data/dictionaries/branch_templates.yaml`, по группам происшествий. MVP:
  - пожар в квартире;
  - ДТП с пострадавшими;
  - остановка дыхания или сердца (инструкции первой помощи по Минздраву);
  - утечка газа.

  Каждый шаблон — 3–5 развилок и 3–4 итога. Тексты инструкций — из официальных памяток, у каждого перехода есть `source`.

### 5.3 Требования
| ID | Требование |
|---|---|
| RF5-01 | Домен `training/domain/branching.py`: `parse_template`, `validate_graph` (все узлы достижимы, у каждого пути есть итог, нет тупиков без итога, циклы только по времени), `step(state, signals) -> state'` — чистая детерминированная функция |
| RF5-02 | Шаг ветвления вызывается на каждой реплике оператора (до генерации ответа, рядом с шагом профиля), при сохранении карточки 112, на событиях ДДС и по таймеру. Таймер — сервер при каждом запросе звонка, плюс `POST /calls/{id}/tick` раз в 5 с с фронта, пока звонок идёт |
| RF5-03 | Узел меняет поведение заявителя: в промпт `applicant_actor` (новая версия v4) уходит «что происходит сейчас» и обновлённые факты; ворота модификатора объединяются с воротами узла. Без модели — офлайн-реплики из шаблона |
| RF5-04 | Ветвление связывает 112 и ДДС: что старший группы докладывает по прибытии (`brigade_actor`) и какие статусы доступны, зависит от пути. Например, «пожар распространился» требует доп. сил |
| RF5-05 | Конец звонка и карточки: экран «Итог ситуации» — итог, путь по развилкам на временной шкале, на каждой развилке «что вы сделали / что было бы при другом решении» со ссылкой на источник |
| RF5-06 | Оценка: блок `details.branch` — итог, развилки, время до ключевых решений. Вес в итоговой оценке по умолчанию 0 (информативно), преподаватель задаёт вес в занятии, как у профиля |
| RF5-07 | Сценарий: включатель «ветвление» и выбор шаблона при генерации; совместимость с существующими 30 сценариями — без ветвления поведение прежнее (выключено → ничего не меняется, как у модификатора) |
| RF5-08 | Преподаватель: просмотр графа сценария (только чтение) в карточке сценария — узлы, переходы, итоги. Аналитика: распределение итогов по группе |
| RF5-09 | Генерация: модель пишет только формулировки узлов под конкретную легенду. Структура графа, условия и итоги — из шаблона. Факты проверяются, как в 3.2 |
| RF5-10 | P2 — редактор графа для преподавателя (добавить развилку, изменить условие), импорт и экспорт YAML |

### 5.4 Файлы
- **Бэкенд:**
  - `training/domain/branching.py`, `training/application/branching.py` (оркестрация с `PsyDirector`), `calls.py`;
  - `integration/assessment_sources.py`, `assessment/domain/branch_scoring.py`;
  - миграция `0020_branching.py`;
  - `data/dictionaries/branch_templates.yaml`, промпт `ai/prompts/applicant_actor/v4.md`.
- **Фронтенд:** `pages/teacher/ScenariosPage.tsx` (граф), `shared/ui/BranchOutcome.tsx`, `SessionReportPage.tsx`.
- **Документы:** ADR-0014, `specs/F5-branching.md`.

### 5.5 Тесты
- **Unit:**
  - `validate_graph` по всем шаблонам — CI ловит битый шаблон;
  - детерминированные пути «идеальный оператор / типичная ошибка / худший случай» для каждого шаблона;
  - бенчмарк в духе мутаций: каждая развилка достижима и меняет итог.
- **Integration:** звонок с ветвлением от ответа до итога через API; повтор с теми же решениями даёт тот же итог (сид).
- **E2E:** итог и путь показаны в разборе.

### 5.6 Приёмка

- [ ] На демо видно: разное решение → разный итог за один звонок не длиннее 3 минут.

### 6.3 Режимы окружения (ADR-0015)
- `AISKRA_APP_ENV`:
  - **prod** — контур заказчика: нет демо-входа (F2), нет `/dev/*`; Swagger только для администратора; cookie `Secure`; уровень логов INFO; внешний ИИ только при явном `allow_external`;
  - **demo** — публичный стенд: демо-вход, баннер «синтетические данные», индикатор генерации ИИ (F1);
  - **dev** — разработка.
- **Проверка при старте:** в prod без TLS-cookie, с паролем БД по умолчанию или с `fake` в `ai.default_provider` при включённых ИИ-функциях → отказ запуска с понятным сообщением (fail fast). `/health` отдаёт режим и версию (git sha).

### 6.4 CI (GitHub Actions)
- **На каждый PR:**
  - `make be-check`, `make fe-build`;
  - сборка `docker compose build`;
  - `docker compose up` с PostgreSQL → миграции с нуля → импорт справочников → `demo-seed`;
  - smoke `tools/browser_smoke.py` (Chrome + Firefox) по 11 экранам трёх ролей;
  - e2e M6 «вызов → карточка → ДДС → отчёт» на fake-моделях.
- **Ночью:**
  - нагрузочный тест (уменьшенный) на PostgreSQL;
  - 20 повторов набора тестов (ловит нестабильные);
  - e2e на реальной модели демо-конфига с лимитом расходов.
- **Защита ветки `main`:** без зелёного CI слияние запрещено.

### 6.5 E2E-сценарии (Playwright, `tests/e2e/`)
1. Преподаватель:
   - генерирует сценарий → утверждает (полностью и частично);
   - создаёт занятие с профилями и ветвлением;
   - мониторинг → отчёт → отзыв → допуск.
2. Оператор 112:
   - входящий → разговор текстом, голосом (fake STT) и без рук;
   - карточка с адресом из справочника → службы → сохранение → оценка с блоком психологии.
3. ДДС: очередь → «Принята» с бригадами → звонок старшему → статусы → запись звонка WAV.
4. Администратор: пользователи, группы, настройки, резервная копия → восстановление, остановка и запуск подсистем, оповещения.
5. Полигон: вход → разговор → озвучка (fake) → перебивание.
6. Отказы:
   - модель недоступна → офлайн-ответы;
   - TTS недоступен → голос браузера;
   - обрыв сети → черновик карточки сохраняется и восстанавливается;
   - перезапуск backend посреди занятия.

### 6.6 Производительность и надёжность на целевом железе
- Целевое железо — 6 ядер, 32 ГБ, без GPU, PostgreSQL 16.
- **Пороги** (`tools/loadtest.py`):
  - 100 пользователей, 20 одновременных занятий, данные за год;
  - отклик API p95 ≤ 2 с (цель ≤ 300 мс);
  - запись ≥ 100 карточек в секунду;
  - отчёт по занятию ≤ 30 с;
  - ошибок 5xx — 0.
- **Отказоустойчивость:**
  - `restart: unless-stopped`;
  - healthchecks;
  - резервная копия по расписанию → восстановление на чистой машине (время замерить и записать).
- **Ресурсы:**
  - память backend при 20 сессиях;

  - рост таблиц за год (оценка по `bulk_seed`).
